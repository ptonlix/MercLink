# Design

## Context

见 `proposal.md`。公开页现在由 `src/public-discovery` 在进程内取数后输出 HTML，不是独立前端。授权提交在 `/authorize/*/submit`，设备码完成在 `/oauth`。支付收银台是支付宝返回的 `payment.action`。通知进入现有 `/api/v1/payments/*/notify`。路由表只有 `buyer` 和 `merchant` 两种受众，Skill 测试会据此核对路径。正式部署是一个应用容器，图片和发布文件都只能进已配置的 S3 或 MinIO。

## Goals / Non-Goals

**Goals:**

- 商家 Agent 下载这一家店的当前店面源码，自由改写后再替换线上公开页。
- 服务端只保存和分发静态字节，激活只改指针。
- 协议路径在激活后仍由本进程处理。
- 店面 Skill 把不能动的事项和激活前验收写成可测试的句子。
- 店铺、商品和订单状态都用事实槽位现渲染，后端变更不用重新激活。sitemap 和下架地址不靠店面自觉。

**Non-Goals:**

- 不在服务端安装、编译或执行商家源码。
- 不做模板库、多店切换或主题市场。
- 不把支付宝收银台、管理页改密或支付验签移进店面。
- 不新增「回跳即成功」的接口，也不新增错误码。
- 不改变买家 Skill 和商家 Skill 已有的购买、目录和支付教法。

## Decisions

### 起始源码是一份店面工程，不是第二套渲染器

新增 `storefront/`，只通过已有公开接口读取店铺和商品，并提交到现有授权路由。它是第一次下载的源码，也带上 Skill 所要求的本地验收命令。没有激活发布时，线上仍走现在的 `src/app` 公开页，避免这次重写内置落地页。

不采用整仓下载。整仓包含 API、支付和密钥配置，Agent 无法被限制在店面内。

### 发布是两份不可变对象加一个指针

追加迁移，增加发布记录和当前指针。源码包与静态目录写入现有对象桶的 `storefront/` 前缀。静态目录至少含 `index.html`，单份源码或静态内容超过 32MiB 时返回 `validation_error`。允许的静态类型限于 HTML、CSS、JS、地图、图片、字体、JSON 和纯文本。拒绝 `.env`、路径穿越和保留路径。

上传使用已有 Redis 限流端口，按商家计数。不把字节写入数据库或本地目录。

激活请求正文必须带 `confirm: true`，与破坏性字段变更同一习惯。未确认返回 `validation_error`。回滚只改指针。旧发布保留，供已打开页面继续读取带哈希的资源；不在激活请求里删除上一份。

### 保留路径优先于店面

分发前先判断保留路径：`/api`、`/authorize`、`/oauth`、`/admin`、`/media`、`/.well-known`、`/skill.md`、`/merchant/skill.md`、`/storefront/skill.md`、`/llms.txt`、`/sitemap.xml`、`/robots.txt`。这些请求永远进现有路由。

营销页和其他非商品 GET 在有激活发布时从对象存储按字节返回。发布清单可以声明未知路径回退到 `index.html`，但回退不能用在保留路径、`/products` 和 `/products/{id}` 上。没有命中文件且未声明回退时返回 404，不把内置页和商家页拼在一起。

事实只有三类，都用槽位，不另做模板库。店铺槽位来自公开店铺缝：展示名、简介、标识、网站、区域、地址。商品槽位来自公开商品缝：名称、封面、公开字段、规格值、库存、可售状态、主币单位价格。订单槽位来自现有订单读取：只有状态 `paid` 才能渲染成支付成功。槽位只做替换，不执行商家脚本。

商品列表和商品规范文档必须带商品槽位。页面若展示店铺或订单状态，也必须带对应槽位。不含这些事实的营销页仍按字节返回。写死价格、库存、店铺资料或支付成功，激活返回 `validation_error`。事实变化后，下一次渲染使用原版式和新事实。

授权外观要统一时，店面页面仍 POST 到现有 `/authorize/*/submit`。`verification_uri` 继续由服务端签发。服务端页面可以在发布声明了对应入口且文件存在时，把人转到店面文档；入口缺失则留在内置授权页，保证设备码仍能完成。

### 新权限不并入现有商品授权

路由表增加受众 `storefront`。下载、创建发布、激活和回滚只属于这个受众，因此现有商家 Skill 路径测试不会被迫写上这些路径。店面 Skill 必须写上它们。

`storefront:write` 只在授权请求包含它时授予。只请求目录权限的批准结果与现在相同。买家权限不变。

### 验收分本地和服务器

本地验收随源码分发，至少检查静态结果没有保留路径、没有支付宝密码输入、没有在未读取订单 `paid` 时显示支付成功，以及展示店铺、商品或订单事实的文档使用槽位且不写死这些事实。Skill 要求失败时不得确认激活，并写明这些事实由服务端每次渲染，sitemap 与下架地址也由服务端执行。

服务器不信任本地检查，也不执行商家脚本。激活前只检查槽位和有没有写死事实，不把当时的店铺、商品或订单状态烤进发布。渲染时才读对应公开缝或订单读取。

`/products/{id}` 在商品不再公开时返回不可收录，不读发布里的旧文档，也不回退到首页。sitemap 只列当前仍公开、且响应不是首页回退的商品地址。

服务器仍拒绝保留路径、秘密文件和超额体积，并在激活后用现有路由处理协议路径。预览由店面开发服务器把 `/api`、`/media`、`/authorize` 和 Skill 代理到本部署，不给正式环境增加跨域。

### Skill 入口沿用现有重写

`/storefront/skill.md` 重写到只读仓库文件的路由，与另外两份 Skill 相同。`llms.txt` 和 sitemap 增加这个地址。商家 Skill 只加一句指向，不写上传和激活步骤。

## Risks / Trade-offs

- [商家页面在支付宝跳回后显示成功] → 不新增改状态的回跳接口。Skill 和本地验收禁止这种文案。账本仍只认验签后的 `paid`。
- [可替换的登录页先把密码送到别处] → 协议仍由服务端完成，但挡不住恶意店面外传。本部署的店主批准 `storefront:write` 才有这个能力。Skill 禁止收集支付宝密码。管理页不进入源码包。
- [设备码页面被店面改断] → 授权提交路径不可覆盖。声明的店面入口缺失时留在内置授权页。
- [激活后内置文案和 JSON-LD 不再约束无事实的营销页] → 店铺、商品和订单状态仍每次按当前数据渲染。写死这些事实的文档不能激活。
- [店面把未知地址回退成首页] → `/products` 与 `/products/{id}` 禁止这种回退。下架地址由服务端返回不可收录。
- [源码包含密钥] → 拒绝 `.env` 和已知密钥文件名。日志不记录包内正文。

## Migration Plan

1. 先追加发布表和对象前缀，不改变现有公开页。
2. 再上线路由、Skill 和未激活的起始源码。已有商家令牌没有 `storefront:write`，不能上传。
3. 店主重新批准需要改页的 Agent 后，才能下载和激活。
4. 回滚应用版本前，先把指针切回内置页。旧对象可留在桶里。不要在回滚时执行商家源码。

## Open Questions

无。体积上限和限流次数写在实现里，不改变上面的拒绝行为。
