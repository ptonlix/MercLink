# Design

## Context

见 `proposal.md`。`loadEnv` 现在把验证码、短信和支付宝密钥列入 `requiredEnvKeys`。`MERCLINK_PAYMENT_PROVIDER=easypay` 可以跳过支付宝，`MERCLINK_DEV_STUBS=1` 只在 development 跳过厂商密钥，生产环境带上它会拒绝启动。买家 Skill 是静态文件 `src/agent-docs/skill.md`，由 `/skill.md` 原样返回。落地页、商品页和 `llmsText()` 把购买写成固定文案。

这一家店仍是一套部署。开关不能变成数据库配置，也不能在请求里重读环境变量。

## Goals / Non-Goals

**Goals:**

- 启动时解析一次买入模式，环境校验、页面、Skill 和用例读同一结果。
- 关闭时进程可以在没有验证码、短信和支付商户密钥的情况下监听。
- 关闭时下单和买家查单在事务和支付端口之前失败。
- `/skill.md` 按模式返回两份正文，标题都是用户 Skill。

**Non-Goals:**

- 不改买家账号、买家令牌或 scope 的内部名称。
- 不删除订单、支付通知或授权路由。
- 不在关闭时自动关闭历史 `pending` 订单，也不调用支付端口取消。
- 不把 `MERCLINK_DEV_STUBS` 扩展到生产。
- 不新增 GEO 监测、第二份商品读取或第二份路由表。

## Decisions

### 纯函数解析开关

新增 `readPurchaseMode`。只接受缺省、空、`0` 和 `1`。`1` 为开启。其他值返回启动失败，错误信息不回显变量值，避免把误填的密钥打进日志。`loadEnv` 在开发桩生产禁令之后调用它。运行时把结果缓存到现有 identity、access 和 commerce runtime，测试沿用现有 reset。路由不直接散读 `process.env.MERCLINK_PURCHASE`。

备选是请求时读环境变量。这和「只在启动时读取」冲突，也会让同进程的 Skill 和接口不一致。

### 关闭时扩大可跳过的密钥

关闭时，`loadEnv` 跳过验证码四件、短信四件、支付宝四件。易支付商户号、密钥和地址也不要求，即使 `MERCLINK_PAYMENT_PROVIDER=easypay`。`DATABASE_URL`、店主手机号和密码、`OAUTH_SIGNING_SECRET`、`APP_BASE_URL`、`REDIS_URL` 和对象存储五项仍必填。

开启时保留现在的规则：未设置支付实现则要求支付宝；`easypay` 不要求支付宝；development 的 `MERCLINK_DEV_STUBS=1` 仍可跳过厂商密钥。生产环境的开发桩禁令优先于买入模式，两种模式都不允许带着它启动。

开启但当前支付实现的密钥不齐时，不另改合同：进程可以启动，新下单在事务前返回 `dependency_unavailable`。这和关闭时的 `purchase_disabled` 分开。

### 失败关闭放在用例入口

`purchase_disabled` 放进现有错误表，业务码 `40302`，HTTP 403，文案固定为 `本部署未开启买入。` 买家下单和买家订单读取先看缓存的模式，再解析身份之外的事务。没有令牌也返回这个码，而不是 401，避免 Agent 接着去申请设备码。重复 `client_order_no` 不把旧订单交回去。

商家 `order:read` 仍走现有订单查询，不调用支付端口补状态以外的现有规则。关闭时买家读取本身被拒绝，因此不会触发「pending 就向支付端口查一次」。

备选是复用 `forbidden`。调用方无法把它和角色错误分开，所以单独给码。

### 授权在发码前拒绝

只含 `order:write` 和 `order:read` 的设备码请求，在写入设备码之前返回 OAuth `invalid_scope`。不创建授权页会话，不发短信。带目录管理 scope 的请求仍进商家登录，不受影响。

`/authorize/buyer` 直接打开时返回不可收录的说明页，不挂载验证码组件，不渲染手机号或密码表单。买家短信和验证码用例入口同样先看模式，拒绝时不调用厂商。

### 两份用户 Skill，一个路径

开启正文继续放在 `src/agent-docs/skill.md`，标题改为用户 Skill，购买步骤保留。关闭正文单独成文，只教公开查询，并写明 `purchase_disabled`。路由按缓存模式选择正文。路径、sitemap 和保留路径仍是 `/skill.md`。

一致性测试按模式检查：开启时买家路径必须出现；关闭时订单路径出现即失败。商家 Skill 两种模式都要对齐路由表。店面 Skill、商家 Skill 和 `llms.txt` 里指向该文档的称呼改成用户 Skill。

### 公开文案随模式变化，商品事实不变

落地页说明、购买引导、商品页复制购买需求和 `llms.txt` 的用户 Skill 说明由同一缓存决定。关闭时不出现购买引导。商品 JSON、Markdown 和 JSON-LD 仍保留规格和价格。接口目录仍列出订单路由，但必须写明关闭时返回 `40302`，不能写成可下单。

实现时改当前已落地的页脚和 `llms.txt`，保留 `接口文档` 指向 `/interfaces`。不要把页脚改回 `API 根地址`。

### 关闭时不跑支付关闭

超时扫描在模式关闭时直接返回，不锁订单，不回补库存，不调用取消。支付通知路由继续挂载。密钥不齐或验签失败时不改状态。密钥仍在且验签成功时，沿用现有「先验签再改支付记录」规则，避免把已经付过的旧单永远停在 `pending`。买家此时仍不能用订单接口看到它；商家订单查询可以看到。

## Risks / Trade-offs

- [升级后未设置变量即关闭买入] → 在 README、`.env.example` 和 PRD 写明必须设 `MERCLINK_PURCHASE=1` 才能保持下单。这是有意的破坏性默认。
- [关闭后历史 pending 不会自动关闭] → 不在没有支付取消的情况下回补库存。要处理旧单，下次启动设为 `1` 并配齐该支付记录对应的商户密钥。
- [买家在关闭后看不到已支付旧单] → 商家订单查询仍可读。不把买家查询悄悄放行，以免和用户 Skill 矛盾。
- [未归档变更也改了 Skill 和 `llms.txt`] → 在当前正文上改。归档时不要恢复「始终教下单」或「不得新增错误种类」。
- [Next 可能在首次请求时才加载运行时] → 模式缓存在该进程第一次构建运行时的环境上，之后不重读。测试必须 reset，避免串模式。

## Migration Plan

1. 先合并规格和启动校验。默认部署不再要求厂商密钥。
2. 再接拒绝路径、授权页和两份 Skill，最后改公开文案和冒烟。
3. 需要下单的现有部署在升级前写入 `MERCLINK_PURCHASE=1`，并保留现有验证码、短信和支付商户配置。
4. 回滚时去掉开关读取并恢复厂商密钥必填。回滚前已用关闭模式启动的进程不会自动重新打开买入。

## Open Questions

无。默认关闭、用户 Skill 名称、新错误码和只在启动时读取都已定。
