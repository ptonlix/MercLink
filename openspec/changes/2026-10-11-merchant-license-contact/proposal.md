# Proposal

## Why

公开店铺介绍只有店名、简介、网站、标识、区域和经营地址。Agent 和访客看不出怎么联系这家店，也看不出营业执照上的主体是谁。Issue #3 要的是推荐录入的联系方式和执照事实，用来理解、发现和提高可信度，不是新的开店门槛。

## What Changes

- 商家 Agent 可以在现有店铺介绍上保存一组可选客服信息和一组可选营业执照。两组都不是发布店铺或上架商品的前提。
- 客服信息是公开客服电话、可选说明和可选二维码。它不是登录手机号，也不能从登录号自动公开。
- 营业执照必须同时有企业名称、统一社会信用代码、法人姓名、注册地址和执照图片。缺任何一项都不能保存。注册地址不覆盖现有经营地址。
- 识别和同意发生在商家 Agent 与用户之间。Agent 必须先读出上述四项并得到用户明确同意，然后才能上传执照图片和写入资料。服务端不做 OCR，也不提供可自填的同意标记。
- **BREAKING**：`PUT /api/v1/merchant/profile` 在原有七个字段之外必须同时提交 `license` 和 `contact`。旧的七字段请求会被拒绝。
- 新增资料图片上传。图片只进已配置的对象存储，公开读取仍走 `/media/{id}`。执照和二维码只能引用本店、对应用途的媒体地址。
- 已发布介绍的落地页、`/index.md`、JSON-LD 和店面槽位使用同一份事实，并标明商家自行填写、本系统未核验。未发布时公开缝不回显草稿。`llms.txt` 仍只放链接。

## Capabilities

### New Capabilities

- 无。

### Modified Capabilities

- `merchant-public-profile`：资料读写和公开缝增加可选 `license` 与 `contact`，并拒绝残缺执照。
- `product-images`：增加店铺资料图片上传，复用对象存储、媒体读取和商家上传限流。
- `public-pages`：已发布介绍展示客服和执照事实，Markdown 与 JSON-LD 使用同一份事实。
- `agent-skills`：商家 Skill 说明推荐录入、先同意再上传，以及新的请求字段。

## Impact

- 追加 `merchant_profiles` 可空列和新的资料图片表。不改已经应用的迁移，不把资料写进 `merchants`。
- 路由表、商家 Skill、店面 Skill、冒烟清单和前端 API 说明要同时改。不新增 OAuth scope，写入仍用 `product:write`。
- 不新增错误码、厂商 SDK、OCR、工商核验、审核队列或「已认证」标记。
- 不改变买家注册、下单、支付、目录字段和商品上架条件。
