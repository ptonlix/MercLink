# Design

## Context

店铺介绍已经是 `merchant_profiles` 的一行，由商家令牌整份替换。公开读取只走已发布的 store seam。商品图上传、`/media/{id}` 和商家级 `image-upload` 限流已经存在。见 `proposal.md` 的动机。

主规格 `merchant-public-profile` 仍用 `validation_error` 这类错误名。资料路由的实现已经包在 `{ code, message, data, timestamp, request_id }` 里。未归档变更 `2026-10-08-api-envelope-and-smoke` 改过同一条需求。本变更不解决这个总冲突，也不恢复顶层 `error`。

## Goals / Non-Goals

**Goals:**

- 用现有资料行和现有媒体路径保存可选执照与客服。
- 让领域规则拒绝残缺执照、错误信用代码、登录号和身份证号。
- 让 Skill 约束「先同意、再上传」，服务端不假装能证明同意。

**Non-Goals:**

- 不调用阿里云 OCR 或工商接口，不新增依赖。
- 不增加 `confirmed` 字段、审核状态或认证标记。
- 不把执照或客服变成发布、上架或开通的条件。
- 不修改 `shared-api-contract`，不新增错误码或 scope。

## Decisions

### 资料仍是一行，执照和客服用成组列

在 `merchant_profiles` 追加可空列，不新建第二份介绍，也不把文案写入 `merchants`。执照五列要么全空，要么全有值。客服三列全空，或电话与二维码至少有一个。经营地址 `address` 保持原列，注册地址单独存放。

不使用自由 JSON。公开页、Markdown 和 JSON-LD 需要稳定字段；未知键继续拒绝。

曾考虑嵌套表。一组可选事实没有独立生命周期，多一张表只会让整份替换多一次写入。

### 图片不进 `product_images`

`product_images.catalog_id` 必填，资料图片不属于目录。新增 `merchant_profile_images`，记录商家、`license` 或 `contact_qr`、类型和大小。字节仍只进已配置的对象存储。`GET /media/{id}` 先查商品图，找不到再查资料图，不新增媒体路径，也不提供删除和图库。

封面不能引用资料图，执照和二维码也不能引用商品图或外链。身份领域只判断 URL 形状和文本规则。图片归属由应用层查到用途和商家后传给领域函数，身份领域不 import 目录领域。

上传路由放在 `app`，编排放在目录应用服务，因为它已经拥有对象存储和限流。限流继续用商家 ID 加现有 `image-upload` 策略，不建第二把计数器。Redis 不可用时不写字节。

### 同意只写在 Skill

服务端无法知道 Agent 是否把四项展示给用户。可自填的 `confirm: true` 不能证明同意，和字段预览那种服务端算出的确认不是一回事。Skill 要求先在对话里读出企业名称、信用代码、法人姓名和注册地址，用户明确同意后才调用上传和 `PUT`。测试锁住这段说明。

上传成功不等于发布。媒体地址一旦被知道就可以匿名读取，所以 Skill 禁止先上传再征求同意。

### 信用代码只做形状和校验位

领域函数按 GB 32100-2015 检查 18 位字符和校验位。字符集是 `0123456789ABCDEFGHJKLMNPQRTUWXY`。这只拒绝明显认错的代码，不表示主体存在。法人姓名拒绝连续 17 位数字和身份证号形状。图片内容不扫描。

测试可用虚构代码 `91310000MA1FL0000N`。Skill 和示例不得写出可通过校验的代码，避免被当成真实主体。

### 公开事实沿用现有缝

已发布 seam 增加 `license` 和 `contact`，没有时返回 `null`，不省略键。未发布仍是 `404`，不回显草稿。

JSON-LD 的 `telephone` 只来自客服电话。三项执照文字写成 `PropertyValue`，名称分别是 `统一社会信用代码`、`法人姓名`、`注册地址`。注册地址不写入 `PostalAddress`。不添加 `taxID`、`founder` 或认证类型。

默认页和可下载起始店面增加对应槽位。已激活且没有这些槽位的店面仍可保留；服务端不把事实写进没有槽位的 HTML。写死这些标签后的值，按现有「不能写死店铺资料」拒绝。

错误继续走资料路由已有的 `apiFailure`。规格里的 `validation_error` 对应该外壳的 `40000`，不另造响应体。

## Risks / Trade-offs

- [旧 Agent 的七字段 `PUT` 会失败] → Skill、路由表和示例同一批更新。没有兼容的缺省合并，否则整份替换会悄悄清空新字段。
- [执照图上传后即可匿名读取] → 不在页面发布前展示；Skill 禁止同意前上传。不把媒体地址放进 sitemap。
- [法人姓名是个人信息] → 只在商家发布后公开，不写入账号，不采集身份证号。
- [未归档的公开页和外壳变更也改了同一条需求] → 归档时保留本变更的字段、通知句和槽位，不要用旧的七字段正文覆盖。
- [信用代码校验位不能证明企业真实] → 页面固定显示 `商家自行填写，本系统未核验。`

## Migration Plan

追加 `016_merchant_profile_facts.sql`。只加可空列、检查约束和 `merchant_profile_images`，不回填，不改 `011_merchant_profiles.sql`。已有介绍的新字段读作 `null`。

回滚时恢复上一版程序即可。新列和新表可留在库里，旧程序按列名读取时不会依赖它们。不写向下迁移。

无。座机和 400 电话已由客服电话的字符规则覆盖；图片在发布前可被知道 URL 的人读取，也已写入规格。
