# Design

## Context

见 `proposal.md`。现在 `CommerceRuntime.payment` 是一个 `PaymentPort`，创建路径把 `provider` 固定写成 `alipay`。`payments.provider` 和 `payments.channel` 已经存在，订单头没有渠道字段。超时任务先在事务里关闭并回补，再调用 `cancelPayment`；取消失败被忽略。领域函数 `applyProviderStatus` 对已关闭订单忽略后续 `paid`，但没有未履约收款。

易支付协议由适配器自己发 HTTP，不引入厂商 SDK。金额仍以整数分进入领域层。

## Goals / Non-Goals

**Goals:**

- 官方支付宝和易支付实现同一个端口，应用层按支付记录上的 `provider` 实例化。
- 进程启动时只配置一个支付实现。下单请求不能指定实现。有限库存不绑定厂商。
- 关闭前先查单。能关单的实现关单成功后才回补；不能关单的实现对有限库存多锁 5 分钟。
- 不能关单的渠道在关闭后把成功收款记成未履约收款。补发或原额退款都不把订单改成 `paid`。

**Non-Goals:**

- 不照搬 sub2api 的浮点金额、多实例负载均衡、前端收银台、回跳即成功，以及一般退款。
- 不接微信，不实现 `submit.php` 跳转模式，不新增回跳页。
- 不把未履约收款写进订单头，也不为它新增订单状态。
- 不新增错误码，不新增第二套支付路由表。

## Decisions

### 端口按支付记录选择实现

保留 `PaymentPort` 的创建、查单、验签和取消。运行时注册 `alipay` 与 `easypay` 两个实现，应用服务只按 `payments.provider` 取一个。领域层不 import 适配器。

取消结果必须能区分「上游已关闭」和「此渠道不能关闭」。易支付返回不能关闭，不能当成关单成功。官方支付宝只有取消成功才进入关闭事务。

备选是让易支付的 `cancelPayment` 也返回 `ok: true`。这会被现有「取消失败才忽略」的写法误当成上游已关闭，所以不采用。

### 启动时只实例化一个当前实现

环境配置 `MERCLINK_PAYMENT_PROVIDER` 只允许 `alipay` 或 `easypay`。进程启动时用它作为新订单的唯一实现。缺少对应密钥或地址时，进程可以启动，但新下单在事务前返回 `dependency_unavailable`，不扣库存。

下单正文不增加支付实现字段。`payment_channel` 继续只表示 `desktop` 或 `mobile`。买家传入 `payment_provider` 或其他实现字段时，沿用现有严格解析，返回 `validation_error`，不写订单。

新订单把该实现写入 `payments.provider`。之后的创建、查单、通知和关闭按这一列取实现，不读当前环境变量。因此把配置从支付宝改成易支付后，旧的待支付订单仍走支付宝。重复 `client_order_no` 返回原订单，不改写这一列。

注册表仍保留两个实现，只为处理已经落库的另一种记录和它的通知。新订单不会在两者之间选择。

备选是下单时由买家选择已启用渠道。当前只有一个店，不需要买家感知厂商，所以不采用。

### 易支付只保存可打开的 https 地址

创建调用 `mapi.php`，商户订单号用支付记录 id。`desktop` 传桌面设备，`mobile` 传 `mobile`，并优先使用绝对 `https` 的 `payurl2`。不读 User-Agent。下单请求的连接地址存到支付记录，供创建和重试使用，不拿它猜测渠道。

只有绝对 `https` 的付款地址写入 `payment.action` 和支付记录。二维码、图片和 `alipays://` 映射为 `payment_retryable`。同一 `pending` 记录再次创建时直接返回已保存地址，不再提交同一个商户订单号。

查单和退款把商户密钥放在 POST 正文里，不放进 URL。通知只接受文档中的字段，签名用常量时间比较。金额在适配器里换成整数分，和支付记录比较。

### 超时分两条路径

官方支付宝：到期先查。已支付且金额一致则改成 `paid`，不回补。未支付则取消。关单成功后才在一个事务里关闭并回补，此后上游不再收这笔钱。关单因已经支付失败时改成 `paid`，不回补。其他失败保持 `pending`，下一轮再试。

易支付有限库存：到期先查。未支付只写入 `stock_release_at = expires_at + 5 分钟`，库存继续锁着。到点再查；仍未支付才关闭并回补一次。取消调用是空操作，不参与是否回补的判断。查单失败不回补。

易支付无限库存没有可回补数量。到期查到未支付后直接关闭。关闭后的晚到收款仍走未履约收款，不改回 `paid`。

### 未履约收款是支付记录的附属，不是订单状态

新表保存一条支付记录最多一条收款：上游单号、整数分金额、状态和失败原因。状态只有 `open`、`fulfilled_manually`、`refunded`、`refund_failed`。

不能关单的渠道在支付已关闭后收到验签通过且金额一致的成功结果时，插入或保持这一条记录，通知回复 `success`。不调用退款。能关单的渠道只保持 `closed`，不记这条收款。买家和拥有该订单行的商家在订单读取里看到它。订单状态仍是 `closed`。

商家路由是 `POST /api/v1/manage/payments/{paymentId}/unapplied-receipt`，正文只接受 `fulfill_manually` 或 `refund`。补发只改收款状态。退款只对 `easypay`、只退原金额；成功改成 `refunded`，失败改成 `refund_failed` 并返回 `payment_retryable`。已完成的收款返回 `conflict`。官方支付宝收款不允许 `refund`。没有把订单标成 `paid` 的动作。

备选是通知一到就自动退款。渠道可能退失败，也会把例外退款做成隐式行为，所以不采用。

### 开发桩和测试边界

`MERCLINK_DEV_STUBS=1` 时易支付走进程内桩，不访问网络。领域规则测试纯函数。通知验签、金额和地址选择用假 HTTP。需要数据库的关闭、宽限期和收款处理走现有 harness。

## Risks / Trade-offs

- [关闭后买家仍可在上游付款] → 订单保持 `closed`，Skill 写明旧链接不再成交。钱只进入未履约收款，由商家补发或退款。
- [5 分钟盖不住数小时后的付款] → 这是接受的缺口。宽限期只覆盖通知延迟，不表示上游已关闭。
- [退款接口失败或已结算] → 收款变为 `refund_failed`，商家到易支付后台处理。系统不重试到成功为止。
- [唯一实现的配置不齐] → 新下单在事务前返回 `dependency_unavailable`，库存不变。未使用的另一家密钥不必配置。
- [启动配置从支付宝改成易支付] → 只有新订单走易支付。旧订单仍按 `payments.provider` 处理。响应里的 `payment.provider` 只说明实际实现，不是让买家再选。

## Migration Plan

1. 追加迁移：付款地址、连接地址、`stock_release_at`，以及未履约收款表。已有支付记录保持 `alipay`，新列为空。
2. 配置易支付商户号、密钥、API 根地址和通知地址。通知地址是 `POST /api/v1/payments/easypay/notify`，同时接受 GET。
3. 先部署端口和关闭顺序。`MERCLINK_PAYMENT_PROVIDER` 未改时，新订单仍是官方支付宝。
4. 回滚应用不能删掉已发出的易支付订单。回滚前要保留查单和通知处理，否则待支付订单无法对账。

## Open Questions

无。渠道 ID 不是协议必填项；第一个上游不配置它，以后需要时再加环境变量，不改变规格。
