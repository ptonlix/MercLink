# MercLink 技术架构

状态：v1  
对应需求：`docs/PRD.md` v1.10  
日期：2026-05-16

本文只回答怎么实现当前 MVP。不引入需求里已经明确不做的能力。

---

## 1. 实现原则

1. **一个可部署应用。** 页面、API、授权、支付通知都在同一个进程里。不拆微服务。
2. **业务规则不写在路由里。** 路由只做认证、解析和返回。规则放在领域模块。
3. **外部服务可替换。** 支付宝、阿里云验证码、短信认证都通过端口调用。领域层不出现厂商 SDK。
4. **一件事一个事务。** 下单扣库存、支付通知改状态、字段破坏性变更，都必须在一个数据库事务里完成。
5. **公开文档和接口共用事实。** Skill 可以手写，但接口路径和错误码以代码注册表为准。不一致时测试失败。

---

## 2. 总体结构

```text
浏览器 / Agent
    │
    ▼
┌──────────────────────────────────────┐
│            MercLink 应用              │
│                                      │
│  页面层     总落地页、商品页、Skill、授权页、超管页 │
│  接口层     /api/v1、OAuth、支付通知    │
│  应用层     注册、下单、字段变更、上下架  │
│  领域层     账号、目录、商品、订单、支付  │
│  端口       短信、人机验证、支付、时钟    │
└──────────────┬───────────────────────┘
               │
        PostgreSQL
               │
     ┌─────────┼──────────┐
     ▼         ▼          ▼
 阿里云验证码  号码认证短信  支付宝 AI 支付
```

Agent 不直连数据库，也不直连支付宝或阿里云。它只调用 MercLink 的 HTTP API。支付私钥、短信密钥、验证码密钥只存在于服务端环境变量。

## 3. 技术选型

| 选择 | 用什么 | 为什么不用别的 |
| --- | --- | --- |
| 语言 | TypeScript | 页面、API、领域类型可以共享。商品字段和订单快照都是结构化 JSON |
| 运行时 | Node.js 24 LTS，当前小版本 24.18.1 | 24 是现在的 Active LTS。26.10.0 更新，但还不是 LTS，不用于生产 |
| 应用框架 | Next.js 16，当前稳定版 16.3.8 | 总落地页、商品页、授权页、超管页和 API 放在一个应用里。使用最新稳定版，不用 canary |
| 领域代码 | `src/domain` 纯 TypeScript | 不依赖 Next.js。规则可以用单元测试直接跑 |
| 数据库 | PostgreSQL 18，当前小版本 18.6 | 18 是现在最新的正式大版本。19 仍是 Beta，不用于生产。小版本跟到当前 18.x |
| 数据访问 | Drizzle | 部分唯一索引、JSON 和显式事务比 ORM 魔法更清楚 |
| 授权服务 | `node-oidc-provider` | OAuth 2.1、PKCE、设备码、刷新令牌轮换已经实现。不自己写授权协议 |
| 密码 | Argon2id | 超级管理员、商家、买家密码都只存哈希 |
| 校验 | Zod | 接口入参和字段值共用同一套解析 |
| 类型检查 | TypeScript `strict`，并用 `tsc --noEmit` | 类型错误不能只靠编辑器发现 |
| 代码规范 | ESLint 扁平配置 + typescript-eslint 类型感知规则 + Prettier | Next.js 官方链路是 ESLint。不并行再上 Biome，避免两套规则互相打架 |
| 单元测试 | Vitest | 与 Vite、TypeScript 同一套转换。领域规则不启动 Next.js |
| 架构约束 | dependency-cruiser | 防止领域层引用页面、数据库和厂商 SDK |
| 无用代码 | Knip | 找出未使用的文件、导出和依赖 |
| 安全扫描 | GitHub CodeQL、Dependabot、Gitleaks、`npm audit` | 分别覆盖代码漏洞、依赖漏洞和密钥泄漏。不叠多套同类扫描 |
| 定时任务 | 进程内每分钟扫描 | 只用于关闭超时未支付订单。不引入队列 |
| 部署 | 一个容器 + 托管 PostgreSQL | 设计伙伴阶段没有第二套基础设施的必要 |

不引入 Redis、Kafka、Elasticsearch、Neo4j、微服务和独立 MCP 进程。短信频率限制和设备码都放在 PostgreSQL。以后接口变成瓶颈，再把限流移到 Redis，不改变领域模型。

## 4. 代码边界

```text
src/
  app/                页面和路由。只调用应用层
  domain/
    identity/         超管、商家、买家
    access/           授权范围、令牌撤销
    catalog/          目录、字段、商品、规格
    commerce/         订单头、订单行、支付
  app-services/       一个用例一个文件
  db/                 表定义和事务
  ports/              端口接口
  adapters/
    aliyun-captcha/
    aliyun-sms/
    alipay/
  agent-docs/         Skill 正文。测试核对其中的路径
```

依赖方向只有一种：`app` → `app-services` → `domain`。`domain` 不能 import `app`、数据库或厂商 SDK。

四个领域模块之间不互相调用内部函数。跨模块只用应用层编排。例如下单时，应用层先问目录模块「这是不是可售规格」，再让交易模块建订单。

## 5. 关键流程

### 5.1 买家首次下单

```text
Agent 调用下单接口
  → 401，响应里带授权元数据
  → Agent 打开授权页
  → 验证码 2.0 通过后，服务端才发短信
  → 短信核验通过，创建买家并设置密码
  → 买家批准 order:write 和 order:read
  → Agent 拿到访问令牌
  → 再次下单
  → 事务内锁定规格、校验上架、扣库存、写订单头和一行订单行、写支付记录
  → 事务提交后向支付宝创建支付
  → 把支付动作返回给 Agent
```

支付宝调用放在事务外。如果创建支付失败，订单保持 `pending`，接口返回可重试错误。重复的 `client_order_no` 返回原订单，不再次扣库存。

### 5.2 支付结果

```text
支付宝通知
  → 先验签，失败直接拒绝
  → 按支付记录号找到 payment
  → 事务内把支付记录改为 paid，再把订单头改为 paid
  → 重复通知不重复改状态
```

查询订单时如果本地仍是 `pending`，先向支付宝查一次，再按支付记录回写订单头。订单头的 `paid` 只是副本。

超时关闭由每分钟扫描完成：锁定到期的 `pending` 订单，关闭支付记录和订单头，按订单行把库存加回，并调用支付宝取消。同一订单只处理一次。

### 5.3 商家开通

```text
超级管理员首次登录并修改密码
  → 填写商家名称、手机号、初始密码
  → 事务内创建商家和默认目录
  → 商家在授权页登录，首次必须改密码
  → 批准后 Agent 获得商家权限
```

商家授权页没有注册分支。停用商家时，撤销该商家全部分授权。

### 5.4 字段变更

兼容变更直接写当前字段，并追加一条 `schema_revisions`。

破坏性变更第一次只计算影响，不写库。带 `confirm` 的第二次请求在一个事务里修改字段、转换或清空不兼容的值、下架不再合法的商品，并写变更记录。

## 6. 数据实现约束

表结构以 PRD 第 11 节为准。实现时补上这些数据库约束：

- 买家和商家的手机号，只在 `deleted_at is null` 时唯一。
- 目录内 SKU 只在未删除时唯一。
- `orders` 的 `(buyer_id, client_order_no)` 唯一。
- `payments.provider_trade_no` 在非空时唯一，用来挡住重复通知。
- 下单和关闭订单时，对 `variants` 行使用 `SELECT FOR UPDATE`。
- `attrs` 和快照使用 `jsonb`。过滤数字字段时用表达式索引，等出现慢查询再加，不预先拆表。
- 订单行和变更记录没有 `deleted_at`，应用层也不提供删除方法。

价格在进入领域层之前就变成整数分。领域层不接受元或浮点。

## 7. 外部适配器

每个端口只暴露领域需要的动作。

| 端口 | MVP 实现 | 领域层看到的结果 |
| --- | --- | --- |
| 人机验证 | 阿里云验证码 2.0，`VerifyIntelligentCaptcha` | 通过或拒绝 |
| 短信 | 号码认证服务 `SendSmsVerifyCode`、`CheckSmsVerifyCode` | 已发送或核验通过。验证码不进本地库 |
| 支付 | 支付宝官方 AI 支付接口 | 支付动作、已支付、已关闭 |

适配器负责签名、重试和厂商错误码转换。应用层只处理自己的错误：验证未通过、短信过于频繁、支付创建失败。

短信发送前必须先通过人机验证，并通过本地频率限制。频率限制失败时不调用阿里云。

## 8. 认证实现

授权服务使用 `node-oidc-provider`，账号数据仍在自己的 `admins`、`merchants`、`buyers` 表里。通过适配器把登录校验接到这三张表，不把用户再存一份到授权库。

访问令牌有效期 15 分钟。刷新令牌轮换，只存哈希，撤销写在 `oauth_grants.revoked_at`。

商家和买家是两类 client 权限，不是两类 OAuth 服务器。授权请求里的 scope 决定页面：

- 含商品管理 scope：商家登录页，无注册。
- 只有订单 scope：买家登录或手机号注册页。

API Key 不进入这条链路。它是另一套中间件，只给明确标记为脚本的密钥使用。

## 9. 页面、发现与 Skill

公开页面由服务端渲染，数据来自同一个商品查询用例，不写第二套读取逻辑。搜索引擎和 Agent 不执行页面脚本也能读到正文。

`/` 是总落地页。它说明服务用途、给出 Skill 和 API 入口，并列出当前已上架商品摘要。商品摘要调用商品查询，不建内容管理表。

发现文件也由应用生成：

- `/robots.txt` 允许 `/`、`/products` 和两份 Skill，不允许授权页、超管页和 `/api`。
- `/sitemap.xml` 只收录仍可公开访问的页面。商品下架或删除后，从地图移除。
- `/llms.txt` 指向总落地页、商品列表、Skill 和 API，不内嵌全部商品。
- 商品页的 JSON-LD 与 API 返回的价格、货币、库存使用同一查询结果。

`/skill.md` 和 `/merchant/skill.md` 放在仓库里。测试检查这两份文档包含当前路由表里的买家路径和商家路径。文档落后于接口时，测试失败。

超管页只有四件事：修改自己的密码、开通商家、停用商家、重置商家密码。不做商品表格，也不进入站点地图。

## 10. 质量门禁

本地和合并前运行同一组检查。编辑器提示不能代替这条门禁。

### 10.1 类型

`tsconfig.json` 至少打开：

- `strict`
- `noUncheckedIndexedAccess`
- `noImplicitOverride`
- `noFallthroughCasesInSwitch`
- `verbatimModuleSyntax`

`exactOptionalPropertyTypes` 先不打开。它和现有页面框架的类型配合容易产生大量无意义修改，等领域代码稳定后再单独评估。

领域层不使用 `any`。外部 JSON 先经 Zod 解析，再进入领域类型。`unknown` 可以出现在适配器边界，不能出现在订单、库存和权限规则里。

### 10.2 规范与静态检查

ESLint 使用扁平配置，启用 `typescript-eslint` 的 `strictTypeChecked`。Next.js 页面同时启用 `eslint-config-next`。格式由 Prettier 负责，ESLint 不再管缩进和引号。

另外两条静态检查：

- `tsc --noEmit` 负责完整类型检查。ESLint 的类型规则不能代替编译器。
- dependency-cruiser 负责依赖方向。`domain` 引用 `app`、`db` 或 `adapters` 时失败。
- Knip 负责删除无人引用的文件、导出和依赖。

### 10.3 测试

Vitest 覆盖领域层和应用层。页面不要求单元测试。

必须有测试的规则：

- 下单扣库存、重复业务单号、超时加回库存。
- 支付通知验签失败、重复通知、状态只从支付记录回写。
- 字段破坏性变更的预览和确认。
- 买家未过人机验证不能发短信。商家授权不能注册。
- 买家令牌不能改商品，商家令牌不能下单。

这些测试使用事务或可回滚的测试数据库，不模拟掉库存锁。外部支付宝、短信和验证码用端口假实现。领域层覆盖率低于 90% 时，检查失败。页面和适配器不计入这个比例。

Skill 路径测试仍然保留。

### 10.4 安全扫描

| 检查 | 时机 | 失败条件 |
| --- | --- | --- |
| Gitleaks | 每次提交和合并 | 发现密钥、私钥、访问令牌 |
| `npm audit --audit-level=high` | 每次合并 | 生产依赖有高危或严重漏洞 |
| Dependabot | 持续 | 依赖和 GitHub Actions 有可用更新 |
| CodeQL | 每次合并 | 新增高危代码扫描结果 |

不把审计警告都当成失败。低危和开发依赖的噪音不阻断合并，但高危必须处理或有明确的到期例外。

### 10.5 命令

```text
npm run format:check
npm run lint
npm run typecheck
npm run test
npm run boundaries
npm run knip
npm audit --audit-level=high
```

`npm run check` 依次执行除审计以外的本地检查。审计和 CodeQL 放在合并流水线。任一失败都不能合并。

## 11. 部署与配置

一个容器监听一个端口。数据库迁移在启动前执行，不在请求里改表。

必须来自环境变量：

- 数据库连接
- 超级管理员初始手机号和密码
- 授权服务签名密钥
- 阿里云验证码和短信密钥
- 支付宝应用私钥和支付宝公钥
- 支付通知地址

缺少任一密钥时，应用拒绝启动。不使用代码里的默认密钥。

日志不记录密码、短信验证码、访问令牌、刷新令牌和支付私钥。

## 12. 实现顺序

与 PRD 第 13 节一致，每步都先写失败测试：

1. 数据库表、超管、商家开通、买家手机号注册、OAuth。
2. 目录、字段、商品、规格和上下架。
3. 总落地页、商品页、发现文件和两份 Skill。
4. 订单行、库存锁定、支付宝支付记录和超时关闭。
5. 用外部 Agent 只读 Skill 跑通买家下单和商家管理。

前一步没有真实事务跑通，不开始下一步。
